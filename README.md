# فهم‌یار — Fahmyar 🧠

**سنجش فهمیدن، نه فقط درستی پاسخ.**

فهم‌یار یک سیستم **تشخیصی آموزشی** است؛ نه یک آزمون آنلاینِ معمولی. به‌جای نمره و رتبه:

1. **ریشهٔ خطا را پیدا می‌کند** — حتی بین‌درسی (مثلاً خطای فیزیک که ریشه‌اش در بدفهمیِ ریاضی است)
2. **سؤال‌های دنباله‌دارِ انطباقی** می‌پرسد تا شواهد کیفیِ کافی دربارهٔ فهم جمع کند
3. **گزارش کیفی** می‌دهد: چه چیزی فهمیده شده، چه چیزی مبهم است، چه چیزی نیاز به مرور دارد
4. **سؤال‌ها را درست‌به‌وقت (JIT) تولید می‌کند** وقتی معلم/دانش‌آموز ارزیابیِ مفهومی را می‌خواهد — نه از یک بانک از‌پیش‌ساخته
5. **هیچ نمره/رتبه/درصد/مقایسه‌ای** بین دانش‌آموزان تولید نمی‌کند — عمداً

> ⚠️ **نمرهٔ آزمون — نه سنجش فهم:** اگر نمرهٔ امتحانی جایی ثبت شود، صرفاً داده‌ای جداست و هیچ‌گاه با «فهمیدن» ترکیب نمی‌شود.

## معماری

```
درخواست HTTP
   │
   ▼
api/ (FastAPI)  ── auth(JWT) ── exam builder ── teacher dashboard
   │
   ▼
engine/
   ├── session_manager.py   ← سقف ۳۰ دقیقه، مکث/ادامه، دو مسیر شروع (موضوع / پاسخ غلط)
   ├── question_selector.py ← اول بانکِ تصویب‌شده ← سپس تولید JIT
   └── inference.py         ← موتور شواهد ۵ وضعیته (بدون عدد)
   │
   ▼
ai/
   ├── model_abstraction.py ← پروایدر قابل‌تعویض: GeminiFree / Mock + روتر + لاگ هزینه + سقف بودجه
   ├── question_generator.py← تولید سؤال JIT با پرامپتِ مقید (JSON ساخت‌یافته)
   └── response_analyzer.py ← تحلیل ساختار استدلال (نه کلیدواژه) → 5 وضعیت
   │
   ▼
graph/ (NetworkX DAG)  +  models/ (SQLAlchemy → SQLite)  +  reports/ (گزارش فارسی)
```

### مسیرهای شروع ارزیابی

- **مسیر A — انتخاب موضوع** (`trigger_type=topic_selection`): دانش‌آموز مفهوم را انتخاب می‌کند → گزاره‌های اصلی همان مفهوم سنجیده می‌شوند.
- **مسیر B — پاسخ غلط** (`trigger_type=wrong_answer`): دانش‌آموز پاسخ غلط می‌دهد → سیستم مسیر حل را تجزیه می‌کند، از گراف دانش `get_root_cause_candidates` می‌سازد (پیش‌نیازها/ابزارهای بین‌درسی)، و پرسش را از **محتمل‌ترین ریشهٔ خطا** شروع می‌کند. مثلاً خطای قانون کولن → ابتدا «توان‌های ریاضی» (ابزار بین‌درسی) پرسیده می‌شود. **پاسخِ سؤال اصلی هرگز به دانش‌آموز داده نمی‌شود.**

### ۵ وضعیت شواهد (هرگز عددی نیستند)

`CONFIRMED` (تأییدشده) · `LIKELY_UNDERSTOOD` (احتمالاً آموخته‌شده) · `UNCLEAR` (نامشخص) · `NEEDS_REVIEW` (نیاز به بررسی) · `INSUFFICIENT_EVIDENCE` (فاقد شواهد کافی)

قواعد ترکیب شواهد (`engine/inference.py`):
1. ≥۲ شواهدِ تأییدکنندهٔ **مستقل** (سؤال‌های متفاوت) + بدون تناقض قوی → `CONFIRMED`
2. ۱ تأیید قوی یا ۲ تأیید ضعیف/وابسته → `LIKELY_UNDERSTOOD`
3. شواهد متناقض → `UNCLEAR`
4. ≥۱ ردکنندهٔ قوی → `NEEDS_REVIEW`
5. بدون شواهد → `INSUFFICIENT_EVIDENCE`

> 🔑 **اصل حیاتی:** موفقیتِ صرفاً محاسباتی (`computational_success`) هیچ‌گاه گزارهٔ اصلی را به `CONFIRMED` ارتقا نمی‌دهد؛ فهمِ مفهومی شرطِ تأیید است.

### جریان تصمیم برای «ادامه / توقف» (`should_continue`)

توقف وقتی: همهٔ گزاره‌های هدف `CONFIRMED`/`NEEDS_REVIEW` باشند · زمان ۳۰ دقیقه تمام شود · دانش‌آموز درخواست توقف کند · سؤالی برای پرسیدن نماند (سقف `MAX_SESSION_QUESTIONS`=۱۲) · فرضیهٔ بین‌درسیِ معلقی نماند.

ادامه وقتی: گزاره‌ای `UNCLEAR` است و زمان باقی است، یا فرضیهٔ ریشهٔ خطای بین‌درسی هنوز نیاز به تست دارد.

## استفادهٔ سریع از API

```bash
TOKEN=$(curl -s -X POST localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"student1","password":"student123"}' | python -c 'import sys,json;print(json.load(sys.stdin)["token"])')

# شروع ارزیابی روی «قانون کولن» (id=6)
curl -s -X POST localhost:8000/api/assess/start \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"trigger_type":"topic_selection","concept_id":6}'

# ثبت پاسخ (با استدلال، نه فقط جواب)
curl -s -X POST localhost:8000/api/assess/1/answer \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"question_id":1,"response_text":"چون نیرو با مجذور فاصله نسبت عکس دارد، بنابراین نصف شدن فاصله نیرو را چهار برابر می‌کند، زیرا فرمول کولن F=kq1q2/r^2 است."}'

# گزارش کیفی (فارسی)
curl -s localhost:8000/api/assess/1/report -H "Authorization: Bearer $TOKEN"
```

## هوش مصنوعی: هزینه، بودجه، کلید

- **پروایدر پیش‌فرض:** `gemini_free` با مدل `gemini-2.0-flash` (پلن رایگان گوگل). کلید را از <https://ai.google.dev> بگیرید.
- **حالت کاملاً آفلاین:** `AI_PROVIDER=mock` — بدون کلید و شبکه؛ پاسخ‌های قطعیِ قالب‌بندی‌شده می‌دهد (مناسب CI و توسعه).
- **ثبت همهٔ فراخوانی‌ها** در جدول `ai_usage_logs` (مدل، توکن، هزینه، نوع وظیفه، زمان، موفقیت/خطا).
- **سقف بودجه:** `BUDGET_LIMIT_USD` (پیش‌فرض ۱۰ دلار؛ پلن رایگان همیشه صفر است). با اتمام سقف، `BudgetExceededError` پرتاب می‌شود.
- **محدودیت نرخ:** فاصلهٔ حداقلی بین فراخوانی‌های Gemini (`GEMINI_MIN_INTERVAL_SECONDS`, پیش‌فرض ۴ ثانیه ≈ ۱۵ RPM پلن رایگان).
- **مقاومت در برابر خطا:** اگر تحلیل پاسخ fail شود → شواهد `UNCLEAR` + `needs_teacher_review=true`؛ جلسه هرگز به‌خاطر خطای AI نمی‌خوابد. اگر تولید سؤال fail شود → fallback به بانک تأییدشده.
- **سؤالات تولیدیِ AI** همیشه با `approval_status=pending` ذخیره می‌شوند و تا تصویبِ معلم از بانک خارج نمی‌شوند (در همین جلسه قابل استفاده‌اند).

## داده‌های اولیه (seed)

- **۱۶ مفهوم** در سه درس: ریاضی (توان، نسبت و تناسب، بردار، تابع، معادلهٔ درجهٔ اول)، فیزیک (نیرو، قانون دوم نیوتن، تجزیهٔ نیرو، کار و انرژی، قانون کولن، قانون اهم)، شیمی (عدد اکسیداسیون، اکسایش و کاهش، استوکیومتری، تعادل شیمیایی، سرعت واکنش)
- **۲۵ وابستگی** (بیش از ۲۰ مورد؛ اکثراً بین‌درسی) — مثال‌ها:
  - ریاضی/توان → فیزیک/کولن (tool) · ریاضی/توان → شیمی/سرعت واکنش (tool)
  - ریاضی/نسبت و تناسب → فیزیک/اهم (tool) · ریاضی/نسبت و تناسب → شیمی/استوکیومتری (tool)
  - ریاضی/بردار → فیزیک/تجزیهٔ نیرو (tool) · ریاضی/تابع → شیمی/تعادل (tool)
  - شیمی/عدد اکسیداسیون → شیمی/اکسایش و کاهش (prerequisite)
  - فیزیک/نیرو → فیزیک/قانون دوم نیوتن (prerequisite)
- **۴۸ سؤالِ از پیش تأییدشده** از بانک (۳ سؤال به ازای هر مفهوم) برای کار بدون AI
- **۴ کاربر دمو** (جدول بالا)

## اجرای تست‌ها

```bash
AI_PROVIDER=mock python -m pytest tests/ -q
```

۱۱ تست: کیفیت دادهٔ seed، پیمایش گراف بین‌درسی، کاندیدهای ریشهٔ خطا، قواعد ۵ وضعیته (شامل «موفقیت محاسباتی ≠ تأیید فهم»)، سقف زمانی، جریان کامل جلسه با mock، کنترل دسترسی.

### تست سرتاسری (E2E) با سرور زنده

```bash
# سرور باید اجرا باشد:
uvicorn main:app --reload

# در ترمینال دیگر:
python test_e2e.py
```

`test_e2e.py` کل چرخهٔ زندگی سامانه را خودکار می‌کند: سلامت سرور ← ثبت‌نام/ورود demo_student ← دریافت مفاهیم ← مسیر A (انتخاب موضوع) ← ثبت پاسخِ غلط + پاسخ اصلاحی ← راستی‌آزمایی گزارش (وجودِ مشاهدات/شواهد/برچسب «⚠️ نمرهٔ آزمون» و **عدمِ وجود نمره/رتبه/درصد**) ← مسیر B (فرضیه‌های ریشهٔ خطای بین‌درسی) ← خلاصهٔ فارسیِ PASS/FAIL با خروج کد ۰/۱. اگر کاربر از قبل وجود داشته باشد به ورود fallback می‌کند. آدرس سرور با `FAHMYAR_BASE_URL` قابل تغییر است.

## محدودیت‌های شناخته‌شدهٔ MVP

- تحلیل پاسخ در **mock** فقط قطعی و ساده است؛ کیفیت واقعی با `gemini_free` حاصل می‌شود.
- ترجمه/تحلیلِ عمیقِ فارسی به کیفیت پرامپت و مدل وابسته است؛ همیشه `needs_teacher_review` را در گزارش‌ها جدی بگیرید.
- سؤالات JIT تا تصویبِ معلم وارد بانک عمومی نمی‌شوند.
- مکانیزم ضدِ تقلب/ضدِ کپی در محیط واقعی لازم است (این MVP پیاده نکرده).
- مقیاس‌بندی: SQLite برای MVP؛ برای تولید به PostgreSQL مهاجرت کنید (فقط `DATABASE_URL` را عوض کنید).

## حریم خصوصی و اخلاق سامانه

- هیچ مقایسه/رتبه/درصد بین دانش‌آموزان در هیچ خروجی‌ای وجود ندارد.
- گزارش هر جلسه شخصی و قابل‌مشاهده فقط برای صاحب جلسه و معلم/مدیر است.
- شواهد کیفی جایگزین گفت‌وگوی انسانی نمی‌شوند؛ تصمیم نهایی با معلم است.
